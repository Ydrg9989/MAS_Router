# Routing LLMs: Architectures and Principles

Modern multi-LLM and agentic systems employ diverse **routing mechanisms** to assign incoming queries to the most suitable model, balancing *accuracy*, *cost*, and *latency*. Below we compare representative methods, highlighting each architecture, algorithm, and evaluation metrics, and then analyze the deeper principles that make them effective. We also discuss analogies from other domains to inspire new routing approaches.

## Representative Routing Methods

- **EvoRoute (Experience-Driven Routing)** – *Guibin Zhang et al., arXiv 2026*. EvoRoute is designed for LLM *agent systems* and frames routing as a **multi-objective (trilemma) optimization** among quality, cost, and latency. It maintains a growing experience base of past query-model outcomes. On each step, it 1) **retrieves** similar past queries and candidate LLMs via semantic matching; 2) **filters** candidates by extracting the Pareto-optimal frontier (models not dominated in accuracy, cost, or delay); and 3) **selects** among those using *probabilistic exploration*: it models each metric as a distribution and uses Thompson sampling to pick a model. In experiments on agentic benchmarks (e.g. GAIA, BrowseComp+), EvoRoute maintained or improved performance while cutting execution cost ~80% and latency ~70%. Its key contributions are *fine-grained, step-wise model selection* and continual policy refinement from feedback. 

- **MasRouter (Multi-Agent System Routing)** – *Yue et al., ACL 2025*. MasRouter explicitly addresses **multi-agent systems (MAS)**, not just single-agent queries. It introduces **MAS Routing (MASR)** as a unified task that includes selecting collaboration mode (e.g. sequential vs parallel), allocating roles to agents, and choosing LLMs. Architecturally, MasRouter uses a cascaded controller network: first it decides a high-level collaboration mode, then assigns roles to agents, and finally routes each agent’s queries to specific LLMs. All decisions are learned end-to-end via supervised training on MAS workflows. Empirically, MasRouter improved code-generation benchmarks (MBPP, HumanEval) over baselines: e.g. +1.8% on MBPP and up to ~52% cost reduction on HumanEval. In summary, MasRouter balances **effectiveness vs efficiency** by jointly optimizing the MAS structure and model choice, yielding a more *cost-effective agent ensemble*.

- **MixLLM (Contextual Bandit Routing)** – *Wang et al., NAACL 2025*. MixLLM formulates multi-LLM routing as a **contextual bandit** problem. It first **enhances query representations** via tags or metadata, then uses lightweight predictors to estimate each candidate LLM’s *quality* and *inference cost* for that query. A meta-decision module then selects the assignment that optimizes a weighted trade-off of quality, cost, and latency. Crucially, MixLLM supports **continual learning**: it continually updates its predictors from online feedback. In experiments MixLLM achieved a very favorable trade-off, e.g. ~97.3% of GPT-4’s answer quality at only 24.2% of the cost. In effect, MixLLM leverages **bandit-style exploration** and prediction of query-model affinity to adaptively allocate models under changing conditions.

- **Tryage (Perceptive Model Selection)** – *Hari & Thomson, arXiv 2023*. Tryage is a **general model library router**. Its “perceptive router” is itself a language model that predicts each candidate model’s performance on the given prompt. It then solves a **multi-objective assignment**: an objective function incorporates predicted accuracy *and* user-specified constraints (flags) such as model size, recency, or security. Users can inspect a Pareto front of trade-offs (e.g. accuracy vs size) and set a tolerance. Tryage was evaluated on heterogeneous datasets (code, text, clinical, patents) and outperformed baselines (e.g. Gorilla, GPT-3.5) in selecting the optimal model: it identified the best model 50.9% of the time vs 23.6% for GPT-3.5 and 10.8% for Gorilla. The method is inspired by the brain’s “thalamic router” and emphasizes **fully contextualized performance prediction** and *user control* over trade-offs.

- **Routesplain (Concept-Based Routing)** – *Štorek et al., arXiv 2025*. Routesplain targets software-engineering tasks (code generation, repair, etc.) and focuses on **interpretability**. It first uses an LLM to extract explicit “concept” labels from the query (e.g. task type, programming language, reasoning complexity). Routing decisions are then based **only on these human-interpretable concepts**. This design yields a router that provides intelligible rationales: “Because this is a Python repair task of medium complexity, we route to Model X.” In tests over 16 state-of-the-art LLMs on 8 code-related benchmarks, Routesplain outperformed any single model in accuracy-cost tradeoff and matched or beat opaque baselines. Notably, Routesplain’s concept-level intervention also allows human operators to tweak or “intervene” in routing by changing concepts.

- **AMRO-S (Ant-Colony Multi-Agent Routing)** – *Wang et al., arXiv 2026*. AMRO-S casts MAS routing as a **semantic-conditioned path selection** (analogous to ant foraging). It introduces three mechanisms: (1) a small supervised LLM for *query intent inference* (a semantic signal), (2) **pheromone tables** specialized by task, where each task maintains its own learned pheromone trail so different tasks do not interfere, and (3) a **quality-gated asynchronous update** that separates routing evaluation from learning to avoid latency overhead. In practice, incoming queries are matched to “paths” of agents via weighted pheromone networks. On several MAS benchmarks and under high load, AMRO-S gave up to 4.7× speedup (with cost reduction) versus static or naively broadcast routing, while maintaining accuracy. The pheromone mechanism also yields *traceable evidence*: one can inspect pheromone intensities to understand routing choices.

- **IRT-Router (Item-Response Routing)** – *Song et al., ACL 2025*. Inspired by educational testing, IRT-Router models each LLM’s “ability” and each query’s “difficulty”. Specifically, it learns a model that predicts the probability a given LLM will correctly answer a query, based on latent difficulty and ability factors. This yields **interpretable parameters**: each LLM’s ability level and each query’s difficulty level are explicit. It also includes an online “warm-up” to handle unseen queries by semantic similarity. In experiments over 20 LLMs and 12 datasets, IRT-Router outperformed baselines in accuracy-cost tradeoff and especially excelled in cold-start scenarios. The IRT framework provides a principled way to incorporate *prior knowledge* of models and queries into routing, balancing performance and cost.

- **Adaptive Bandit (PILOT)** – *Panda et al., arXiv/EMNLP 2025*. This method also casts routing as a **contextual bandit** under budget constraints. It embeds both queries and LLMs into a common space (learned from offline preference data) so that affinity is explicit. Then it applies a LinUCB-style bandit (PILOT: Preference-prior Informed LinUCB) to iteratively improve routing with online feedback. Crucially, it adds a **knapsack-based budget policy**: given a user’s cost budget, it solves a multi-choice knapsack to select a cost-efficient allocation across queries. In short, PILOT adapts to evolving query streams without ground-truth labels, using online learning to handle unknown settings and budget constraints.

- **IPR (Quality-Tolerant Routing)** – *Feng et al., arXiv 2025*. IPR is an industry-scale router focusing on **user-specified quality tolerance**. It trains lightweight *quality predictors* (on 1.5M annotated prompts) to estimate an LLM’s response quality. Users set a tolerance parameter τ ∈ [0,1] that specifies how much quality loss they accept for cost savings. The router then enforces quality≥τ and minimizes cost subject to that. Key innovations include frozen shared encoders with small adapters (so new models plug in quickly) and a massive benchmark (IPRBench) for training. Deployed on a cloud platform, IPR achieved ~43.9% cost reduction while matching the quality of high-end models, at low latency. This demonstrates how *fine-grained quality estimation + explicit user control* can guide routing decisions.

## Comparative Analysis

Despite varied techniques, these methods share a few design themes.  First, **multi-objective optimization** is central: most aim to *maximize answer quality* while *minimizing cost/latency*. For example, EvoRoute explicitly optimizes a Pareto front of (performance, cost, delay), and Tryage’s objective also integrates accuracy with resource flags. IPR even lets users directly tune the quality-cost trade-off. In practice this often means **trading off** cheaper models vs. stronger ones, selecting minimal models that still meet quality.  As a survey notes, “well-designed routing systems can outperform even the most powerful single model by leveraging specialized capabilities across models while maximizing efficiency”.

Second, the **timing of decisions** varies. All methods above use *pre-generation routing* (decide model before answering), but some allow multistage cascades (e.g. MasRouter’s cascade controllers, or the multi-arm exploration in EvoRoute). In contrast, **cascading methods** would run small models first then escalate, but most contemporary routers simply pick one model per query. A few approaches (not reviewed above) also consider post-generation signals or human feedback for refinement. 

Third, the **information used** differs:  
- **Static query features:** Many use only the query text or simple metadata (e.g. MixLLM uses tags, Routesplain uses extracted concepts, evoRoute uses semantic embeddings).  
- **Performance prediction:** Some train predictors of model accuracy or difficulty (MixLLM’s predictors, IPR’s quality estimator, IRT-Router’s learned ability curves).  
- **Learning from feedback:** EvoRoute and AMRO-S incorporate *experience* or performance logs (EvoRoute’s knowledge base, AMRO-S’s pheromone updates). MixLLM, PILOT, and IPR leverage either offline labels (IPR) or online bandit feedback (MixLLM, PILOT). This leads to **adaptivity**: methods that learn online can handle changing model pools or query distributions.

Fourth, in **operational context**: MasRouter and AMRO-S target multi-agent pipelines explicitly, where tasks decompose across several agent LLMs, whereas others (MixLLM, Tryage, IRT, IPR) assume a single user-model interaction. Finally, some emphasize **interpretability** (IRT-Router, Routesplain) while others focus purely on efficiency (MixLLM, EvoRoute).

**Strengths and limits:** Algorithms like Pareto filtering (EvoRoute) and IRT bring principled multi-objective reasoning and interpretability, but can require significant historical data or model metadata to tune. Bandit-based methods (MixLLM, PILOT) naturally adapt and need less supervision, yet they may explore suboptimal models initially. Concept-based routers (Routesplain) are transparent but rely on reliable concept extraction. Ant-colony (AMRO-S) excels under concurrency by decentralized learning, but its gains depend on task homogeneity and well-trained intent models. Industrial solutions (IPR) can leverage massive labeled data for fine control, but require that labeling effort. 

## Underlying Principles

Why do these methods work well? At a high level, they exploit **model specialization** and **adaptivity**. LLMs differ in strengths (some better at reasoning, others faster or multilingual), so routing leverages the right tool for each query. Many approaches use **specialized expert allocation** akin to Mixture-of-Experts (MoE) models: a lightweight gating mechanism picks a subset of experts per input. For instance, MixLLM’s bandit is effectively learning a gating policy, and Routesplain’s concept-route pipeline is a hard-coded gating. This mirrors how MoE layers train a sparse gating network to route tokens to expert sub-networks, but at a higher level it routes whole queries among separate LLMs.  

Another key principle is **multi-objective optimization**. Routing is intrinsically a Pareto problem: no single model is best on all metrics, so one must **balance trade-offs**. Methods either explicitly compute Pareto frontiers (EvoRoute) or allow user-defined trade-offs (IPR’s τ, Tryage’s flags). This multi-criteria view is analogous to scheduling or resource-allocation problems in systems engineering, where one must trade time, quality, and cost. For example, a cloud scheduler might assign tasks to VMs based on SLA penalties vs. compute expense, which is conceptually similar to routing queries to LLMs under latency and cost budgets. Indeed, one method (PILOT) formalizes a **knapsack-style budget constraint**, reflecting classical combinatorial optimization.

Learning from **feedback and experience** is another common theme. Evolutionary or RL-inspired strategies (EvoRoute’s Thompson sampling, AMRO-S’s pheromone updates, PILOT’s bandit) allow the router to adapt when query distributions change or new models appear. This mirrors ideas in online learning and adaptive control. The success of IRT-Router also shows the power of borrowing from other fields: modeling LLMs and queries as “students” and “test items” (difficulty × ability) comes from psychometrics, yet it yields an interpretable routing score. Similarly, AMRO-S adapts the ant-colony metaphor (decentralized pheromone learning) to dynamically evolving multi-agent workloads, exploiting its inherent ability to find near-optimal paths in fluctuating environments. 

In sum, effective routing schemes **dynamically match query “difficulty” or context to model capability**, often using lightweight predictors or learning algorithms, while simultaneously respecting constraints. They incorporate *task semantics* or *user goals* (e.g. language, domain, resource limits) to prune the search space. They often employ *sparse gating*: rather than querying all LLMs, they select a small subset to save cost. This conditional computation idea is a recurring principle: just as a Mixture-of-Experts network activates only a few experts per input, routing systems activate only the needed LLMs. Finally, interpretability or structured design (e.g. concept-level routing, mode/role controllers in MAS) can improve trust and debuggability, suggesting that combining *symbolic or semantic reasoning* with statistical methods is fruitful.

## Analogies and Future Directions

Routing LLM queries connects to many broader CS concepts. For example, **network routing algorithms** (shortest-path, load balancing) also deal with multi-criteria decisions (latency, bandwidth, reliability). One could imagine graph-based routers that view models and tasks as nodes (analogous to GraphRouter), using graph neural networks to predict good paths. **Queueing theory** and **scheduling** in operating systems similarly aim to allocate jobs to processors to optimize throughput and fairness – insights from those fields (e.g. priority queues, multi-queue scheduling) might inspire adaptive LLM dispatch. 

**Mixture-of-Experts (MoE)** in deep learning is a close analogy: MoE layers learn gating networks (often using gating logits) to route tokens to experts. Future routing methods could embed a trained gating LLM inside a larger model, letting the router also exploit hidden activations. **Conditional computation** and **early-exit networks** in neural net research (where inference can stop early when confident) are analogous to cascading (e.g. run small model first then escalate). 

**Game theory or auctions** might inform multi-agent routing: one could envision each LLM “bidding” its quality per token-cost for each query, and a mechanism selects the winner, balancing global constraints. Similarly, **multi-armed bandits and reinforcement learning** from online learning continue to be fruitful: beyond LinUCB and Thompson sampling, techniques like *contextual Thompson*, *Neural bandits*, or *meta-RL* could adapt even faster.  

From AI more broadly, **curriculum learning** suggests that queries themselves could be ordered or filtered (an LLM routing analogous to a curriculum could assign tasks to models in increasing difficulty). Also, **neural architecture search** (NAS) sometimes uses surrogate models to predict performance – similarly, surrogate performance models are used in MixLLM and IPR. 

In summary, new routing architectures might combine **symbolic planning (concept extraction, rule-based modes)** with **statistical learning (bandits, neural predictors)**. They might incorporate richer feedback: for instance, using reinforcement learning where the “router” is itself an agent that gets rewards for balanced performance. Or they could leverage **federated learning** to train routers without sharing raw queries, as hinted by “Federate the Router” works. Cross-domain ideas (e.g. from control theory, operations research, swarm intelligence, or even biological neural systems) are likely sources for future innovation in LLM routing.
